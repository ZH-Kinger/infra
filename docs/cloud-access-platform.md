# 云账号自助平台

员工在一个地方完成：看自己有哪些云账号和权限、申请开账号、申请云账号权限、申请访问凭证、
查看云账号资产。管理员在另一套页面里处理待办、名册、执行失败的申请、离职停号和审计。
面板和 `delivery` CLI 共用同一个后端，规则只写一份。

代码在 `src/delivery/`，部署见 [deploy/panel/README.md](../deploy/panel/README.md)。

**登录方式的现状**：线上跑的是**飞书登录**（`delivery serve --auth feishu`，也是默认值）。
公司 IAM 登录（oauth2-proxy + OIDC，含 `delivery login --iam` 的设备码）代码已经写好、
配置模板在 `deploy/panel/`，但**还没有启用**，需要 IT 先建好 OIDC 应用。下文凡是提到
oauth2-proxy 的地方都是这条未启用的路径。

## 1. 不能退让的规则

| # | 规则 | 落在哪里 |
|---|---|---|
| R1 | **任何开通、授权、发凭证，都必须有一条已通过的飞书审批。** 执行前后端实时查飞书审批实例，状态是 `APPROVED`、审批定义、发起人、表单里的申请单号都对得上才执行，并且至少有一位**不是申请人**的审批人点了通过（只有本人或自动通过的不算，approval.json 的 allow_self_approval 可放开）；不信回调内容、不信本地状态 | `approval.py` `verify_approved()`；`flows.py` 的 execute / claim_password 都先调它 |
| R2 | 员工只能给自己申请：权限申请的目标子账号必须是名册里已确认属于本人的号 | `flows.py` 提交时校验 |
| R3 | 申请只能从两处选：管理员预先定义的模板（用户组、角色、时长上限），或采集来的权限策略目录。策略目录由服务端规则把关：提权、身份管理、密钥管理、账单、审计类策略内置禁用（身份 / 账单 / 审计整个产品线只放只读），规则文件只能追加禁用；**自定义策略默认不开放**（名字看不出能做什么，执行身份自己的策略也是自定义策略），要逐条写进 `allow`；最长天数按风险定。用户不能提交目录外的策略、角色 ARN、用户组名 | `catalog.py`、`policies.py` |
| R4 | 访问凭证**只以密文落盘**：审批通过后服务端立刻签发，加密存进申请单，飞书审批评论里只给一个带密钥的查看地址（`/c/<申请单号>#<密钥>`）。**密钥从不落盘**，只在链接的 fragment 里（浏览器不发给服务端，不进访问日志、不进 Referer）——服务端没有主密钥，自己也解不开，`tickets.json` 整个泄漏拿不到凭证。链接可以反复打开，每次打开记一笔（谁、何时、从哪）。secret 不写日志、不进通知卡、不进任何评论正文。凭证没能送达即作废（删号删策略删 AK），清没清干净如实记账；残留的 AK 单独记进 `orphan_ak_ids`。链接外泄时管理员可以立刻作废（删密文 + 删云上的号和密钥）。初始密码只能在开通后 7 天内领取一次，且子账号必须是这张申请单新建、名册里没有对应给别人 | `sealed.py`、`flows.py` `_offer_credential()` / `view_credential()` / `revoke_now()` / `_cleanup_issued()` / `claim_password()` |
| R5 | 执行身份最小权限，且**开通与发放分成两把 AK**：开通身份只有开号、加组、移出组、扮演模板角色这几个动作，云上明确禁掉建号 / 发 AK / 造策略；发放身份只用于长期访问凭证，资源级收窄到 `staff-*` / `tempak-*` 子账号与对应策略（两朵云都实测过越界被拒，见第 9 节）。每次写云前核对凭证属于目标云账号。目前从面板服务器的环境变量读取（`DELIVERY_EXEC_*` / `DELIVERY_ISSUER_*`）；改用实例角色是后续项 | `provision.py`、`identity/executor-policy.*.json`、`deploy/panel/cloud-policies/` |
| R6 | 员工身份只认 `feishu_union_id`（公司 IAM 规范） | 登录层（当前是飞书登录；oauth2-proxy 那条未启用） |
| R7 | 所有状态变化记审计：谁、何时、对哪张申请单、做了什么；审计只追加 | `tickets.py` 事件表、`identity/review.log` |
| R8 | **离职处理只动账号，不动数据。** 自动只做「停用」（可恢复），删号必须管理员逐个确认；受保护的号（服务号、面板自己的身份）代码和云策略两处各拦一道 | `offboard.py`、`deploy/panel/cloud-policies/` |

## 2. 角色

| 角色 | 能看到 | 能做 |
|---|---|---|
| 员工 | 我的云账号与权限、我的申请、我能领取的凭证、我所在云账号的资产概况 | 提交申请、撤回自己未审批的申请、领取已批准的凭证和初始密码 |
| 管理员 | 待办、全员名册、全部申请、全部资产、审计 | 名册审核、重试执行失败的申请、关闭申请、维护模板、确认离职删号（面板或飞书卡片） |

管理员名单只按 union_id（`identity/admins.json`）。**管理员自己提交的申请同样走飞书审批**，
管理员身份不能跳过 R1。

## 3. 申请类型

| 类型 | 员工填写 | 审批通过后执行 | 员工领取 |
|---|---|---|---|
| 开账号 `account` | 模板（哪个云账号、默认加入哪些组）、希望的用户名、用途 | 建子账号、加入模板里的用户组、写入人工对应（名册下次刷新生效） | 控制台初始密码（一次性，强制首次登录改密）|
| 云账号权限 `permission` | 模板（如「OSS 只读」）、目标子账号（只能选自己的）、用途、时长 | 把子账号加入模板的用户组 | — |
| 云账号权限（按策略）`permission` + 模板 id `policy` | 权限列表里勾选 1–10 条策略、用途、时长（不超过所选策略里最短的上限） | 把策略直接授予本人子账号 | — |
| 访问凭证 `credential` | 模板（桶 + 目录 + 权限）、使用方、有效期 | 审批通过即签发，密文存单子、密钥在评论里的查看地址 | ≤12 小时走 STS；超过则建带时间窗的子账号 + 长期 AK，到期删号 |
| 服务访问凭证 · 程序用 `credential` | 同上，外加**用途里写清服务名和负责人** | 同上 | 给 lakeFS 这类长期在跑的程序用，所以基本都落在长期 AK 那条路上 |

「服务访问凭证 · 程序用」只是凭证模板的一种，流程和普通凭证完全一样，区别在于：

- 有效期上限 **90 天**，且 90 天是**代码里的硬顶**（`catalog.STS_MAX_HOURS` / `MAX_CREDENTIAL_HOURS`）——
  任一模板把 `max_hours` 填过头，模板目录**加载期**就抛错，整页申请打不开。调小它要先上模板、再上代码；
  回滚反过来。已经发出去的凭证不受影响。
- 用途里写服务名和负责人：这把钥匙不属于某个人的日常操作，到期那天断的是服务。
  面板和飞书私聊的到期提醒都按申请人发，负责人写不清就没人接得住。

有时长的权限到期后由 `delivery requests sweep` 移出用户组、撤销授予的策略。开通前子账号本来就在的组 / 已直接授予的策略、同一子账号还有别的未到期申请给的，都不收回。
「本来就在」只在第一次开通时判断，且不包括别的申请单加进去的组：到期前续期、开通失败后重试，都不会让限时权限变成永久。

申请页每一项都标出对本人的状态：可申请、已拥有（权限快照里子账号已在全部用户组，可续期）、
申请中、不可申请（附原因）。「已拥有」只是提示，快照没有或没采全时按「未知」显示为可申请。
模板可选填 `category`（如「存储」「AI 训练」），只用于申请页分类筛选，不影响开通内容，改分类也不影响审批中的申请。

权限列表（`GET /api/policies`）列出本人有子账号的每个云账号里的全部策略，标出：可申请、已有（快照里直接授予
或经用户组继承）、申请中、不开放（附原因），并给出风险和最长天数。按策略申请的单子在开通前除了核对飞书审批，
还要确认每条策略仍在**当前**目录里、没被规则禁用、最长天数没被调低，否则不开通。

申请单详情给申请人和管理员「去飞书查看审批」的链接（飞书 AppLink，PC 与移动端各一个，客户端 7.3.0 起支持）。

### 3.1 凭证策略里的三条 OSS 真机结论

凭证策略由 `grants.build_policy` 生成，动作名在 `platforms.py` 的 `StorageDialect` 里（只有一份）。
下面三条是真机踩出来的，改动作清单前先看一眼：

| 结论 | 表现 |
|---|---|
| `HeadObject` / `GetObjectMeta` 在 RAM 里**都映射到 `oss:GetObject`** | 做不到「只给元信息、不给下载」。要元信息就等于给了下载，别在审批里承诺这种粒度 |
| 桶开了版本控制时，带 version id 的 GET/HEAD 走的是 **`oss:GetObjectVersion`** | 少了它的表现是「能下载，但带版本号的请求 403」，看着自相矛盾。lakeFS 这类 S3 兼容客户端默认带版本号，线上踩过。它只是读同一个对象的某个版本，不扩大 Resource 范围 |
| S3 兼容客户端建连先探地域，缺 **`oss:GetBucketLocation`** 就连不上 | 报错和权限八竿子打不着，排查会跑偏。这个动作不返回任何数据，白给 |

另外两条一直有效的老规矩：桶信息动作（`GetBucketInfo`/`GetBucketStat`/`GetBucketAcl`/`GetBucketLocation`）
**独立成一条、桶级、绝不叠 `oss:Prefix` 条件**（桶级请求不带 prefix，叠上去必被拒）；
每条语句都叠时间窗，包括桶信息那条。

### 3.2 到期提醒

同一件事分两个收件人，缺哪一边都会漏：

- **申请人**：飞书私聊，**两档 —— 到期前 7 天、到期前 1 天各一次**（`flows.Flows.REMIND_TIERS`）。
  每档记自己的事件（`expiry_reminded:7`），发过的不再发。只提前 3 天对 90 天的服务凭证太晚，
  负责人可能正在休假。本来就只开几天的权限不提醒（开通消息里已写了到期时间）。
- **管理员**：待办页同时列「7 天内到期」和「已经过期还没收回」两类（第 7 节）。
  本人可能休假、可能已经离职，而到期那天断的是服务。

已知代价：发送失败的那一档**会被消耗、不再重试**（先记事件再发，避免并发重复发）；
老单子（只有无档位的 `expiry_reminded` 标记）升级后会多收一条 7 天档提醒。

## 4. 申请单状态

```
提交 ──► 待审批 ──► 已通过 ──► 执行中 ──► 已完成 ──► 已到期回收
          ├► 已拒绝    └► 已关闭   ├► 执行失败 ──► 已关闭
          └► 已撤回   （没经他人    │      └──(管理员重试)──► 执行中
                        同意）      └► 待开通（资源类）──► 已完成 / 已关闭
```

- 状态只能按上图流转，其他转换一律拒绝。
- 「已到期回收」除了从「已完成」进，也从**执行失败 / 已关闭**进：凭证签发出来却没送达的单子停在那两个状态，
  云上那把长期 AK 得有人删。只让「已完成」能回收的话，它永远等不到定时任务。
- 「开通中」「提交中」超过 30 分钟没有进展视为中断，标成失败，由管理员核对后重试或关闭。
- 飞书里通过后又被撤销（实例 `reverted`）的审批，一律按未通过处理。
- 「已通过」只由同步飞书审批状态得到；同步可以是员工或管理员打开申请单，或 `delivery requests sweep`
  定时任务——都只是「去飞书查一次」，结论以飞书接口返回为准。

## 5. 离职停号

人离职之后云账号还开着，以前没有任何触发器会提醒 —— 要等某天有人恰好打开面板那一页。
现在由定时任务 `delivery identity iam-remind` 每天跑两轮（10:00 / 16:00），
**检测到离职就自动停用，删号仍然要人确认**。代码在 `offboard.py`。

### 信号分强弱，处理也分两档

| 信号 | 判据 | 面板做什么 |
|---|---|---|
| **强** | 飞书状态 `is_resigned`（已离职），或 IT 的公司 IAM 标了 `is_active=false` | **自动停用**：关控制台登录 + 把 AK 全部置为 Inactive。两样都能恢复，记一条 `disabled`，发卡片给管理员 |
| **弱** | 飞书通讯录里按 union_id 和公司邮箱都找不到；飞书状态是「冻结」或「已退出企业」 | **不动账号**，只记一条 `suspect` 等人拿主意 |

弱信号不自动停，是因为飞书对「已离职」和「不在应用可见范围内」返回的是同一个结果，
冻结多半是长假或临时封禁 —— 停了会让在职的人的任务当场断掉。

**一轮超过 3 个人被判离职，一个都不停**（`offboard.MAX_AUTO_PEOPLE`），全部记成待确认。
飞书或 IT 的接口抖一下就可能把一批在职的人标成离职，那时候停得越多事故越大。

### 停用、删号、恢复

- 停用 = 删控制台登录配置 + AK 置 Inactive。**记下这次关掉了什么**（`login` / `keys`），
  恢复时照着开回去，不碰别的。停用中途失败的会记 `incomplete`，下一轮接着停。
- **删号要管理员确认**，在面板（`#admin/iam`）或飞书卡片上点。删号顺序是
  删 AK → 出组 → 摘策略 → 解 MFA → 删登录配置 → 删用户，没删干净的逐项回报。
- **只删账号本身**：桶里的文件、数据集、实例一概不碰 —— 那些属于主账号，不属于子用户。
- 点「没离职」= 恢复（`restored`）或排除嫌疑（`dismissed`），**之后不再自动停这个号**，
  除非管理员把这条记录删掉。
- 名册里这个号**不归这个人**（`unverified`，多半是 IT 那边属性值导错了）时，面板**拒绝删号**，
  只给「没离职」按钮 —— 一键删掉的可能是别人在用的号。

### 谁不能碰

只处理名册里**确认归属某个人**的号。服务号、面板自己的三个执行身份、`power-application-user`
这类按前缀硬拦（`offboard._PROTECTED_CLOUD`：`panel-` / `power-` / `tempak` / `wuji-` / `rl-` /
`finance` / `data-tran`），**云上执行身份的策略里另有一份 Deny**。两边各自独立，
一边写漏了另一边还在 —— 所以**改名单要改两处**，现网策略副本在 `deploy/panel/cloud-policies/`。

九章用的是另一套更窄的名单（只挡 `panel-` / `power-`）：九章登录名全是 `wuji-` 开头
（`wuji-wangyuran`），套云上那套前缀等于把整个平台挡光。

### 九章：没有接口，只能提醒

九章（AlayaNeW）没有可调的账号接口，面板动不了它的号。但它**照样进离职流程**：
记一条待确认、进飞书卡片和待办页，文案是「去控制台停用」；管理员在控制台处理完，
回来点一下销账，它才从待办里消失（**只记账，不碰云**）。
不列出来的话，一个离职的人在九章上的号没有任何地方会提醒 —— 线上漏过一次。

### 记在哪、审计在哪

- 离职记录 `identity/offboard.json`（0600，读改写全程 flock —— 定时任务和面板是两个进程）。
- 停用 / 删号 / 恢复每个号一行，追加进 `identity/review.log`。
- 状态：`disabled`（已停用，待确认）、`suspect`（待确认，没停过）、`deleted`、`restored`、
  `dismissed`。前两个是「等管理员拿主意」。

## 6. 飞书卡片按钮回调

离职卡片上的「确认删除」「没离职」两个按钮**在飞书里直接点**，不用再打开面板。
原先卡片只有一个「去确认」链接：打开面板 → 找到那一行 → 再点一次，一件五秒钟的事拆成三步，
于是就拖着，而拖着的那几天号一直开着。

代码：`card_hook.py`（纯校验逻辑）+ `server.py` 的 `/feishu/card`。

### 三道门，缺一不可

这条路**没有登录会话**，飞书只带来一个 open_id —— 能伪造请求的人把 open_id 填成管理员就能删号。
所以：

1. **验签**：`X-Lark-Signature` = `sha256(时间戳 + 随机串 + Encrypt Key + 原始 body)`。
   **没配 Encrypt Key 就拒绝一切回调**，不是「先放行等配好」。
   验签算的是**原始字节**，不是重新序列化的 JSON。
2. **Verification Token** 常数时间比对（和审批回调同一把）。
3. 点的人必须在管理员名单里：拿 open_id 去飞书换 union_id 再比（名单里存的是 union_id）。

顺序是**先验签、再解密、再比 token**：反过来的话，解密会拿攻击者可控的密文当输入，
而 token 的对错在验签之前就能试出来。同一个 `event_id` 重投只回结果、不重复执行
（飞书 3 秒没收到 200 就重发）。

### 配置要点

| 在哪 | 配什么 |
|---|---|
| 飞书开发者后台 | 「事件与回调 → **回调**配置」订阅 `card.action.trigger`（不是「事件」那一栏），回调地址 `https://cloud.wuji-tech.com/feishu/card` |
| 同上 | **必须配 Encrypt Key**，并填进面板的 `DELIVERY_FEISHU_CARD_ENCRYPT_KEY`；面板没配就一律 403 |
| 面板环境 | `DELIVERY_FEISHU_VERIFY_TOKEN`（与审批回调共用）、`DELIVERY_FEISHU_APP_ID/SECRET`（换 union_id 要用） |
| nginx | **放行 `/feishu/card`**：飞书的服务器不在公司网里，要绕过 IP 白名单（`deploy/panel/nginx-cloud-panel-common.conf` 已有这条 location） |

URL 校验（challenge）那一次**也是加密的**，所以解密排在 challenge 判断之前，
否则回调地址根本存不下来。

### 两个真机坑

- **飞书发的时间戳是 Go 的 `time.Time.String()` 格式**（`2026-09-23 11:03:52.993 +0800 CST m=+123`），
  不是文档写的数字时间戳，而且精确到纳秒（Python 的 `%f` 只吃 6 位）。认不出来的话防重放的
  时间窗形同虚设。认不出的格式**不拒绝**，只打日志跳过新鲜度检查 —— 真正的门是验签。
- **Card JSON 2.0 没有 `note` 组件，也没有 `action` 容器**（真机试出来的：分别回 200861 / 200621）。
  灰字用 markdown 的 `<font color=grey>`，按钮并排用 `column_set`。1.0 的写法照搬过来整张卡发不出去，
  而发不出去 = 管理员什么通知都收不到。仓库里 1.0 的卡（reclaim / drift / build / move）保持原样，
  别顺手改成 2.0 元素。

## 7. 待办页

管理后台的**默认落地页**（`#admin/todo`，接口 `GET /api/admin/todo`，代码 `todo.py` + `web/todo.js`）。

管理后台有八页，每页回答一个问题，但没有一页回答「现在该干什么」：离职待确认在 IAM 属性表页、
开通失败在申请页、无主账号在人员页和体检页各有一份、密钥老化在体检页。
一件事散在几页的结果是，除非挨页翻，否则什么都不会被处理。

**分组只看后果，不看数据来源**：

| 分组 | 装什么 |
|---|---|
| 要紧的 | 安全敞口（离职的人还能登、IAM 里已离职但云登录名还挂着）或有人被卡住（开通失败、号开了但登录名没发给 IT）、卡住整条链路的配置缺失 |
| 该处理的 | 台账漂移（对应不上、没登记、属性增量没发）、凭证快到期 / 已过期、九章要人去控制台停 |
| 顺手做的 | 密钥卫生（该轮换、没人用），汇总成一行 |

其他约定：

- **排序和分组算在服务端**。飞书卡片、命令行、网页要给出同一个「最要紧的是什么」，
  放前端的话三处各写一份，迟早互相矛盾。
- 排序是：分组 → **挂得久的在前** → 能批量处理的在前。没有时间戳的沉底。
- **依据旧了就降级**：比如 IAM 对账数据超过 3 天，基于它的事项降到「该处理的」并标注
  「先刷新一次再动手」—— 过期数据不该点亮导航上的红点。各数据源的新鲜度单列一块显示。
- **零云调用**：全部来自本地文件和快照，每次打开都能跑。
- 每一类各自 try，**一类读坏了只让那一类缺席**（记进 `errors` 并在页面上说明），不让整页打不开。
  导航角标上的数字和这一页同一份计算。

## 8. 定时任务与失败告警

面板服务器上的 systemd 单元（`deploy/panel/`）：

| 单元 | 干什么 | 频率 |
|---|---|---|
| `delivery-iam-remind` | 离职检测：自动停用 + 提醒管理员（第 5 节） | 每天 10:00 / 16:00 |
| `delivery-sweep` | 同步飞书审批、到期回收权限和凭证、到期提醒、开账号对应到名册 | 建议每 10 分钟 |
| `delivery-refresh` | 权限快照 + 映射提案 + 人员名册 | 见部署文档 |
| `delivery-moves` | 数据搬运任务推进 | — |
| `delivery-assets` | 云资产快照采集 | 每天 |
| `delivery-buckets` | 桶清单采集 | 每天 |
| `delivery-backup` | `identity/` 本地快照备份 | 每小时 |

`iam-remind` 的提醒频率**靠 `--every-hours` 去重，不靠定时器压**：定时器跑勤一点没关系
（新离职的人当天就能被发现），同一批人 24 小时内只发一条 —— 天天重复的提醒等于没有提醒。
去重状态读不到时**照常提醒**。

### 失败告警

上面**每个单元都接了 `OnFailure=delivery-unit-failed@%n.service`**：崩溃、超时被杀、
依赖导入失败时私聊管理员（走面板自己的飞书应用，不依赖群机器人 webhook）。

为什么要这一层：任务的告警是任务自己跑完之后发的，进程根本没跑起来或中途被杀时，
它拿不到报告也就发不出告警 —— 一个每天跑两次的任务可以连着挂好几天没人知道。

告警卡片分级（`notify._TEMPLATES`）：蓝 = 待办、橙 = 要留意、红 = 真出事了。
**什么都用红色的话，红色就不再意味着任何事**，收的人一周之后就不看了。

## 9. 凭证前缀：内部 / 外部分家

| 谁发的、发给谁 | 子账号前缀 | 策略前缀 |
|---|---|---|
| **面板**发给内部同事 | `staff-` | `staff-oss-auto-` |
| **机器人**发给外部使用方 | `tempak-` | `temp-ak-auto-` |
| 跨云迁移交给对方云的源端钥匙 | `tempak-move-<单号>` | 同外部 |

以前两边都是 `tempak-`：面板发给同事的和机器人发给供应商的，在 RAM 控制台上长得一模一样，
只能靠显示名分辨 —— 而出事那一刻，「这把钥匙在公司里还是在公司外」是最先要回答的问题。

跨云迁移的钥匙**按外部算**：跨云的机制是把源端 AK/SK 写进对方云的迁移任务配置里，
由对方云拿着它来读我们的桶。它离开了我们的边界，撤不回来，只能轮换（`move_creds.py`：
只读 + 只限这次的前缀 + 默认 14 天时间窗，搬完立刻删，不等到期）。

**改前缀等于绕过云上那道闸**：执行身份的云策略按这些前缀收窄资源，
改名必须同步改云上 `wuji-panel-issuer` 那条策略，现网副本在
`deploy/panel/cloud-policies/aliyun.wuji-panel-issuer.json`。
撤销和到期清理**两套前缀都认**（`grants.policy_name`）—— 只认新前缀的话，
历史上发出去的外部凭证永远清不掉。存量的不改名，到期自然清理。
