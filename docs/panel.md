# 云权限面板

面板地址 `https://cloud.wuji-tech.com`，飞书登录。代码在 `src/delivery/`，
部署见 [deploy/panel/README.md](../deploy/panel/README.md)，设计取舍和踩坑记录见
[云账号自助平台](cloud-access-platform.md)。

一条链，五步：

```text
申请  ──►  飞书审批  ──►  面板开通  ──►  台账  ──►  到期 / 离职回收
（员工）   （不是本人      （写云、下发     （申请单    （定时任务检测，
            的人点同意）    凭证或密码）     即审计）     删号要人确认）
```

两条不能退让的：**任何开通、授权、发凭证，都必须有一条已通过的飞书审批**；
**离职只动账号，不动数据**。面板和 `delivery` 命令行共用同一套后端，规则只写一份。

## 覆盖哪些平台

| 平台 | 面板能自己开号 / 收号 | 备注 |
|---|---|---|
| 阿里云 `1704065796538912` | 能 | 建号、加组、加 PAI 工作空间、发凭证、停号、删号 |
| 火山引擎 `2111674479` | 能 | 同上，但**没有 STS**，凭证一律走长期 AK + 时间窗策略 |
| 九章（AlayaNeW） | 不能 | 没有可调接口。面板只管申请、审批、台账、离职提醒 |
| TurboAI（曦望） | 不能 | 同九章 |
| 自建服务（`internal`，如 MLflow） | 没有账号可开 | 授权就是那张申请单本身，网关逐请求来问。代码已完整，**现网还没上线模板** |

九章和 TurboAI 在代码里是「人工登记平台」（`platforms.MANUAL`），**不进 `platforms.ALL`** ——
进去的话申请模板、凭证发放、体检都会以为能调接口，体检页曾经因此整页打不开。

## 能申请什么

申请项都是**模板**（`identity/request-templates.json`），加一项不用改代码。模板目录
**在加载期校验**：字段拼错、时长超上限、还留着 `<待建：…>` 占位符，都会让申请页整页
打不开 —— 一个悄悄失效的模板比一个打不开的页面难查得多。现网 15 条，按类型：

| 类型 | 举例 | 审批通过后 |
|---|---|---|
| `account` 开账号 | 阿里云子账号 | 面板建号并做完整套初始化，见[下一节](#建号的数据初始化) |
| `permission` 云账号权限 | 算法组权限、加入工作空间 · 杭州 | 加组 / 加工作空间成员 + 开个人目录 + 建数据集 |
| `credential` 访问凭证 | 数据访问凭证 · 下载、TOS 凭证 · 上传 | 当场签发，密文存进申请单，审批评论里只给一个带密钥的查看地址 |
| `resource` 资源开通 | 阿里云 ECS / RDS | 配齐了创建参数的（阿里云 ECS）面板直接开；没配的停在「待开通」等人建完回来登记 |
| `storage` 数据目录 | 新建数据目录 | 停在「待开通」—— 代码能建，但执行身份还没有那两个数据桶的写权限 |
| `datatype` 数据类型 | 新增数据类型 | 直接写进数据类型词表，「新建数据目录」里立刻能选 |
| `transfer` 数据迁移 | 数据迁移 | 登记 + 走审批，由 `delivery requests moves` 推进 |
| `service` 内部服务 | （现网暂无） | 网关逐请求问 `POST /api/service-access` |

桶、机型、镜像、数据类型只能从模板给的白名单里选，用户提交不了目录外的策略、角色 ARN、
用户组名。权限申请只能给**名册里确认属于自己**的子账号；凭证申请没有这个门槛 ——
它常常是替外部合作方申请的。

**访问凭证不问「要短期还是长期」**，填多久就是多久：≤12 小时走 STS（到点自灭），
超过就建一个带时间窗策略的子账号发长期 AK（12 是阿里云 `AssumeRole` 的硬顶，上限 90 天）。
火山**一律走长期路径**，哪怕只申请一小时 —— 它认不认 `Policy` 参数没有取证过，
静默忽略等于把整个角色的范围发出去。

## 员工怎么用

浏览器打开面板，飞书扫码登录。你只看得到自己的东西。

**提申请**：「申请」页选一项填表 → 提交 → 面板**以你的名义**发起飞书审批 →
「我的申请」看进度。待审批的可以自己撤回。**只有你自己点了同意不算数**，至少要有一位
不是申请人的审批人点通过，否则单子被直接关闭 —— 管理员自己提的单也一样。

```text
提交中 ──► 待审批 ──► 已通过 ──► 开通中 ──► 已完成 ──► 已到期回收
            ├► 已拒绝            ├► 开通失败（管理员可重试）
            └► 已撤回            └► 待开通（要人去建的那几类）
```

卡住了：待审批很久没动就去飞书催人（面板每分钟同步一次，不会漏）；**开通失败**找管理员
重试，**账号多半已经建好了，别去手工再建一个**；**待开通**是面板做不了这一类、
等管理员建完回来登记，不是卡住；**已关闭**多半是只有你自己批了，重新提一张找别人批。

**控制台初始密码**在「我的申请」里领，一次性，首次登录强制改密，**开通后 7 天内**有效。
云账号开了企业 SSO 的话面板不发密码 —— RAM 密码登录在开了用户 SSO 之后就失效了。
企业账号能登的前提是登录名已写进公司 IAM 的 `cloud_accounts`，这步面板自动做；
**没做成的话开通结果第一句就是「他现在登不进去」**，看到这句找管理员重试。

**AK/SK 自己去控制台签发**，面板不代办 —— 代办意味着面板要经手你的 secret，
而整套设计的前提就是面板不持有明文。

**个人开发目录**：阿里云建号时会给你开一个（默认带杭州
`wuji-algo-dev-hz/<组>/<登录名>/`，之后申请新加坡工作空间会合并进同一条策略），
你能读、写、删自己这个目录，但传不成公共读的。组里只有只读权限，所以**没有这条策略
就一个字节也写不进去**，而在 PAI 里挂载着用又一切正常 —— 症状是「AK/SK 一写就 403、
换一把还是不行」，别误判成 AK 坏了。

**拿到访问凭证**：凭证不写在飞书评论里，评论里给的是
`https://cloud.wuji-tech.com/c/<申请单号>#<密钥>`。`#` 后面那段是密钥，浏览器**不会**把
它发给服务端 —— 不进访问日志、不进 Referer，服务端存的是密文、自己也解不开。
所以它可以反复打开（换机器、重装环境、同事接手都行，每次打开都记一笔），
但**丢了就真的取不回来**。别转发 —— 拿到链接就等于拿到凭证。

页面上给好了环境变量、地域和外网 Endpoint。两个坑：阿里云那几行里
`ALIBABA_CLOUD_IGNORE_PROFILE=TRUE` 别省（`~/.aliyun/config.json` 会盖掉环境变量）；
**用错地域的 endpoint 会被直接 403**，看着像凭证无效，其实不是。火山 `ve` / `tosutil`
喂凭证的方式和阿里不一样，面板「CLI」页有实测用法。

凭证能干什么严格按申请的来：「下载」不含上传，「上传」不含下载，**两者都不含删除**。
到期前 7 天和 1 天面板会飞书私聊你。如果这把凭证给的是长期在跑的程序，申请时
**在用途里写清服务名和负责人** —— 到期那天断的是服务，而提醒只发给申请人。

命令行同样能走完全程：`delivery login` / `request new` / `request list` /
`request show` / `request withdraw`。

## 管理员怎么用

管理员名单在 `identity/admins.json`（`emails` 或 `union_ids` 任一命中即算）。
**改它等于改「谁能看到全员的账号、邮箱、权限」，走代码评审**，不要在云控制台上开权限
来代替。名单为空 = 没有人是管理员。管理员自己提的申请同样走飞书审批。

**每天从待办页开始**（`#admin/todo`，默认落地页）。管理后台九页各回答一个问题，
但没有一页回答「现在该干什么」—— 离职待确认、开通失败、无主账号、密钥老化散在四五页，
结果是除非挨页翻否则什么都不会被处理。待办页把它们算成一张清单，**分组只看后果**：
要紧的（有人被卡住 / 安全敞口）→ 该处理的（台账漂移、凭证到期）→ 顺手做的（密钥卫生）。
排序算在服务端，三个入口共用同一份结论；依据旧了会降级并标注「先刷新一次再动手」。

**审批在飞书，不在面板。** 面板只做两件事：以申请人的名义发起审批实例，
以及在开通前**实时回查**它 —— 状态是 `APPROVED`、审批定义 / 发起人 / 表单里的申请单号
都对得上，并且至少有一位不是申请人的审批人点了通过。不信回调内容、不信本地状态。
通过之后又被撤销的一律按未通过处理。

**开通失败**：「申请与开通」页每张失败的单子有重试按钮，重试是安全的 —— 建号有
`user_created` 守着不会重复建，后面每一步都幂等，重试还会重新实时核对飞书审批。
原则是：**账号已经建好之后的步骤，失败只写进结果文案、记事件、进待办页，
不把整张单判失败** —— 判失败会让人以为什么都没发生、跑去手工再建一个号。
所以看到 FAILED 先读结果文案，它写明了做到哪一步。

**名册**（`identity/people.json`）是生成物，由 `delivery refresh` 重建，**不要手改**。
人工介入只有两处：「人员与名册」页确认账号归属（云上手工开的号推不出主人时进待确认）；
「人工登记」页录九章 / TurboAI 的账号名单，那张表**必须带 `as_of`** —— 人工数据过时的
方向是漏报，登记之后新开的号不在表里，那个人离职时离职检查完全看不到它。

**离职**：`delivery identity iam-remind` 每天 10:00 / 16:00 各一轮。强信号
（飞书 `is_resigned` 或公司 IAM `is_active=false`）**自动停用**（关登录 + AK 置 Inactive，
都能恢复）；弱信号（通讯录里找不到、冻结、已退出企业）**不动账号**，只记待确认 ——
飞书对「已离职」和「不在应用可见范围内」返回的是同一个结果，冻结多半是长假，
停了会让在职的人的任务当场断掉。**一轮超过 3 个人被判离职，一个都不停**：
接口抖一下就可能把一批在职的人标成离职，那时候停得越多事故越大。

删号必须逐个确认（面板 `#admin/iam` 或飞书卡片），**只删账号本身**，桶里的文件、
数据集、实例一概不碰；名册里这个号不归这个人时面板**拒绝删号** —— 一键删掉的可能是
别人在用的号。九章 / TurboAI 的号面板动不了，但照样进流程：记待确认、进卡片和待办页，
文案是「去控制台停用」，你处理完回来销账。

**凭证**：申请单详情页的「撤销」删密文 + 删云上的号和密钥，链接外泄时用这个。
到期回收由 sweep 做，**「开通失败」「已关闭」这两个状态也能进回收** —— 凭证签发出来却
没送达的单子停在那儿，只让「已完成」能回收的话，云上那把长期 AK 永远等不到定时任务。

**只能手工做的**：九章 / TurboAI 的开停删号；没配 `resource_type` 的资源（如 RDS）；
新建数据目录；改 RAM 的管理性操作（用 `power-application-user`，不在面板手上）。
登记资源开通结果时**要填机器可读的实例 ID** —— 那是唯一一个「开通那一刻就知道主人是谁」
的时机。

常用命令（全部见 `delivery --help`，多数已由定时任务在跑）：

```bash
delivery serve                     # 面板服务（默认 --auth feishu）
delivery requests sweep            # 同步审批、到期回收、到期提醒、自动补那几类
delivery refresh                   # 权限快照 + 映射提案 + 人员名册
delivery identity iam-remind       # 离职检测 + 自动停用 + 提醒
delivery hygiene --check-status    # 体检：人走了号还在、AK 老化、AK 没人用
delivery doctor                    # 飞书应用体检：一条命令探完会调的所有接口
delivery requests backfill --region hz --who a,b --apply   # 给已有账号补工作空间 + 目录 + 数据集 + 开发目录策略
```

排查顺序：「系统状态」页（只读本地文件，不调外部接口，所以它永远打得开）→「体检」页
→ 申请单的事件表 → `journalctl -u delivery-sweep` → `delivery doctor`。
在面板机上**别用 root 跑写 `identity/` 的脚本**，会把文件改成 root 属主、面板直接挂掉；
写操作一律 `sudo -u delivery`。

## 建号的数据初始化

一张「阿里云子账号」申请通过之后，面板做的不止 `CreateUser`。按真实顺序：

```text
1  建 RAM / IAM 子账号          create_user           幂等守卫 user_created
2  加入默认用户组                add_to_group          阿里 wuji_Algorithm / 火山 wuji_group
3  开控制台登录                  enable_console
4  加入 PAI 工作空间             add_workspace_member  ─┐
5  开个人 OSS 目录               make_dir               ├ 模板列的每个地域各做一遍
6  建 PAI 数据集（CPFS + OSS）   create_dataset        ─┘
7  发开发目录读写策略            ensure_dev_policy + attach_policy
8  写进公司 IAM 的 cloud_accounts / 关联到名册 / 审批评论贴登录地址
```

**只有前两步失败会把整张单判成失败**，第 3 步往后全都不会 —— 账号那时已经建好了。
所以「单子是绿的」不等于「八步都做完了」，得看结果文案。代码在 `flows.Flows._run`
和 `flows.provision_workspace`。

- 建号时就把**安全邮箱**写上，之后要补就得管理员一个个去控制台点。手机号现在拿不到
  （飞书应用没有 `contact:user.phone:readonly`）。
- 默认组是阿里 `wuji_Algorithm`（73 个子账号里 52 个在里面）、火山 `wuji_group`。
  不默认加的话每个人都得再走一张权限单，只是让人多等一次。
- **建号那一刻就开控制台登录**，不等人来领初始密码 —— 企业 SSO 开了之后领密码是死路，
  号建出来了却没有登录配置，人拿企业账号也进不去。
- 工作空间列在**地域登记表** `identity/workspaces.json` 里（现网 `hz` = 杭州 640957 +
  桶 `wuji-algo-dev-hz`，`sing` = 新加坡 284761 + `wuji-algo-dev-sing`），模板只引用 key。
  **加一个地域 = 加一条登记 + 在模板里填这个 key，不碰代码**，一个地域出问题不影响别的。
- 第 5 步在 OSS 里放的是一个 **0 字节占位对象**（OSS 没有真目录），只为了让人在控制台里
  看得见；目录没开成就不建数据集 —— 那多半意味着桶名或地域配错了，这时建出来的数据集
  看着正常、挂载时才炸。第 6 步 **CPFS 和 OSS 各建一条，缺一条人就少一个挂载入口**。
- 第 7 步**建策略用发放身份、挂策略用开通身份**（见[权限控制](#权限控制)），
  且只给这张单批的地域；「第二张单会不会抹掉第一张授的」由 `ensure_dev_policy` 读回
  云上正文再合并来保证 —— 不靠「把所有地域都授了」去绕，那等于发出这张单没批的范围。
- 第 8 步写 `cloud_accounts` **不成，人就登不进去**，所以它的失败文案顶在结果最前面 ——
  写在末尾的话申请人读到「已新建子账号 X」就停了。审批评论里贴登录名、云账号、
  控制台地址和怎么登，**不含任何密钥**；贴在审批下而不是私聊，因为私聊卡片会被后面的
  消息淹掉，而审批实例是这次开号的权威记录。

第 7、8 步失败由 sweep 每轮自动补（`retry_dev_policies` / `retry_iam_writes`）——
必须自动补，因为单子这时已经是绿的 `DONE`，而重试只认 `APPROVED` / `FAILED`，
**人再也点不了**。

**初始密码**不在评论里也不自动发：员工自己在面板领，面板现场调 `reset_password` 生成，
领之前再核对一次飞书审批。限制是 7 天内、只能领一次、子账号必须由这张单新建、
名册里没有对应给别人 —— 否则一张很久以前没领的单子，可以把后来同名的别人的账号密码
重置掉。

**给存量账号补齐**用 `delivery requests backfill`，和建号走同一个 `provision_workspace`。
两个坑：`--apply` 必须配 `--who` 点名（自动圈出来的候选里可能有已经离职、撤过权限的人，
把他们重新加进工作空间是一次没经过审批的扩权）；**按每个人真实的组，不是模板里那个
默认值** —— 默认是 `general`，实测 51 个人里只有 9 个在 `general` 下。组的结构没有任何
地方登记过，只存在于 OSS 对象键里，所以只能现扫。

**名册怎么来的**：`identity/people.json` 由飞书通讯录（或 IT 导出的 CSV）、云上权限快照、
人工登记表三份合成，靠**邮箱**关联、落到 **union_id** 上 —— 邮箱、工号、姓名都会变
（公司已有 27 个 username 漂移、两次登录事故）。名册里 `accounts` 只放**已确认**的对应，
待确认和有冲突的放 `pending`：用户视图只展示 `accounts`，映射错一条用户看到的就是别人的
权限清单。采集不完整时**名册不重建** —— 映射提案是从云上用户列表推出来的，
某朵云采集失败时拿它重建会把这些人的账号全部抹掉。

## 权限控制

三层，互不替代。

### 一、面板自己的云身份

面板在**每朵云上有三个子账号**，三把不同的 AK，云上策略各自收窄。现网策略副本在
`deploy/panel/cloud-policies/`，**以云上为准**，改完重新导出覆盖。

| 身份 | 干什么 | 云上明确够不着的 |
|---|---|---|
| `panel-collector` | 只读采集 | 一切写动作（一条大 Deny 兜底） |
| `panel-executor` | 开通：建号、开控制台登录、加组 / 出组、**挂策略 / 摘策略**、离职停号删号 | **建策略**（没有 `ram:CreatePolicy`）、**发 AccessKey** |
| `panel-issuer` | 发放：在 `staff-*` / `tempak-*` 上建号、发长期 AK、**建策略**（`temp-ak-auto-*` / `staff-oss-auto-*`，阿里那份还有 `wuji-dev-dir-*`） | 真人子账号（资源级只到那两个前缀）、开控制台登录、挂任何系统策略 |

**单独哪个身份都发不出「内容任意 + 挂在真人身上」的策略**，这是这套切分的全部意义：
executor 能把策略挂到真人身上，但造不出策略正文；issuer 能造任意正文，
但它的 `AttachPolicyToUser` 资源列表里只有 `staff-*` / `tempak-*` 这两类自己发的号 ——
连它自己建的 `wuji-dev-dir-*` 都挂不上去。所以建号第 7 步是**两个身份接力**。
图省事合成一个身份就等于把这道闸拆了；`devdir.POLICY_PREFIX` 只加在 issuer 的
`ram:CreatePolicy` 白名单里，**绝不能加到 executor 上**。

executor 手上还是有重的东西（挂任何自定义策略、建号、删号），挡它的是两处 Deny：
`AdministratorAccess` / `AliyunRAM*` / `AliyunSTS*` / `AliyunIMS*` / `AliyunKMS*` /
`AliyunCloudSSO*` 这类系统策略挂不上去；受保护的号（`panel-*` / `power-application-user` /
`finance` / `Data-tran` / `wuji-*` / `rl-*` / `tempak*` / `staff-*`）上的写动作全部 Deny。
**改 RAM 的管理凭证是 `power-application-user`，不在面板手上**，它也在那张名单里。
这份名单**代码和云策略各有一份，改一处就是丢掉一半保护**
（`offboard._PROTECTED_CLOUD` + 两份 executor 策略）。

别把阿里那边的印象套到火山上：**阿里三份策略的 Allow 几乎都带
`IpAddress: 120.79.167.166`，火山三份一条 IP 条件都没有**，火山 executor 的受保护号
Deny 也窄一截。

面板进程**确实握着 executor 的 AK**（开通和离职停号都在进程里调云），所以护栏不是
「面板没有凭证」，而是那把 AK 被收窄过加上面这些 Deny。凭证从环境变量按云账号分开配
（`DELIVERY_EXEC_*` / `DELIVERY_ISSUER_*`），每次写云前核对它确实属于目标云账号 ——
配错账号时宁可失败。

### 二、给人的权限

**用户组** —— 绝大多数人只在一个组里：阿里 `wuji_Algorithm`（OSS 侧只挂着
`AliyunOSSReadOnlyAccess`）、火山 `wuji_group`。

**个人开发目录策略**（`devdir.py`）—— 每人一条 `wuji-dev-dir-<登录名>-<哈希>`，
框住 `wuji-algo-dev-hz/<组>/<登录名>/`，给读写**删**（删必须给：连自己写错的文件都删不掉
的目录实际上是不可用的，人会绕到别处去写），另有一条 **Deny `PutObjectAcl`** ——
不授予 ACL 动作还不够，`PutObject` 本身收 `x-oss-object-acl` 头、服务端按 `oss:PutObject`
判，「上传的同时设成公共读」只有显式 Deny 才封得住。

两个坑：桶信息那条语句**绝不能叠 `oss:Prefix`**（桶级请求不带 prefix，叠上去必被拒，
线上「拿了凭证访问不了桶」就是这个）；**`${ram:UserName}` 那条路是死的** ——
阿里云没有表示调用者用户名的条件关键字，写进 Resource 语法合法、保存成功、然后被当成
字面十六个字符去匹配，挂上了、报成功、人还是写不进去，哪儿都不报错。

**临时访问凭证**（`grants.py`）—— 给外部方的。能力三者正交：`list` 只看清单不能下载 /
`download` 才给下载 / `write` 上传但不含任何删除。**每条语句都叠时间窗 Condition**，
服务端逐次调用判时间，**泄漏也随到期自动失效**，删号只是清理残留；末尾一条 Deny 挡掉
所有删除和改 ACL。和开发目录策略**刻意相反**（那条不叠时间窗、并且给删），
别把两者的策略互相抄。动作清单是真机试出来的（`platforms.py`），最容易踩的一条是
`HeadObject` / `GetObjectMeta` 在 RAM 里都映射到 `oss:GetObject`，
**做不到「只给元信息不给下载」**。

**凭证前缀内外分家**：面板发给内部同事的是 `staff-` / `staff-oss-auto-`，机器人发给
外部方的是 `tempak-` / `temp-ak-auto-`。以前两边都是 `tempak-`，在 RAM 控制台上长得
一模一样 —— 而出事那一刻「这把钥匙在公司里还是在公司外」是最先要回答的问题。
撤销和到期清理**两套前缀都认**。

**策略目录**（`policies.py`）—— 内置禁用清单挡住提权、身份管理、密钥管理、账单、审计
几类，**规则文件只能追加禁用**；**自定义策略默认不开放**（名字看不出它能做什么，
而执行身份自己的策略也是自定义策略）。风险等级决定最长天数：高 30 / 中 90 / 低 180。

### 三、面板内部

管理员名单不从云上权限反推（「有 `AdministratorAccess` 就算面板管理员」）：那把
「能改云资源」和「能看全公司的权限分布」绑死了，后果是任何人只要给自己挂上云超管，
就同时拿到了面板上所有人的身份数据。名单没配 ⇒ **没有人是管理员**，而不是所有人。

普通用户只看得到自己。**凭证只以密文落盘**（`sealed.py`，AES-256-GCM，每份一把新的随机
密钥，密钥从不落盘、只在链接的 `#` 之后），服务端没有主密钥、没有「管理员一键查看」，
`tickets.json` 整个泄漏也拿不到凭证。**审计只追加**：申请单事件表（含每一次打开凭证
链接）加 `identity/review.log`。`identity/` 下文件 0600、目录 gitignored ——
里面有全员邮箱、申请人的姓名手机号、权限快照。

## 定时任务与退出码

面板服务器上的 systemd 单元，文件在 `deploy/panel/`：

| 单元 | 干什么 | 频率 |
|---|---|---|
| `delivery-sweep` | 同步审批、到期回收、到期提醒、自动补 IAM 属性和开发目录策略 | 1 分钟 |
| `delivery-buckets` | 重新生成「数据迁移」能选哪些桶 | 1 分钟 |
| `delivery-moves` | 推进在途的搬运任务 | 5 分钟 |
| `delivery-probe` | 外部探活：自建服务的地址还打得开吗 | 5 分钟 |
| `delivery-refresh` | 权限快照 + 映射提案 + 人员名册 | 20 分钟 |
| `delivery-backup` | `identity/` 本地快照备份 | 每小时 |
| `delivery-iam-remind` | 离职检测 + 自动停用 + 提醒 | 每天 10:00 / 16:00 |
| `delivery-assets` | 云资产快照采集 | 每天 03:20 |

`buckets` 一分钟一轮是因为那份清单同时是白名单：跑得慢意味着删掉的桶还留在申请页上，
有人照样能选它、提单、走完审批，最后在搬运那一步才炸。`iam-remind` 反过来 —— 跑得勤
没关系，提醒去重靠 `--every-hours 24`，天天重复的提醒等于没有提醒。

退出码分四级，**读日志和告警都靠它**：

| 码 | 意思 | 后果 |
|---|---|---|
| `0` | 干净的一轮 | — |
| `3` | 跑完了，但某张单子有问题；已经打印、已经记进单子 | `SuccessExitStatus=3`，**不告警**。这些问题在待办页上 |
| `1` | 这一轮没干成活（整步抛异常、存储读不了、到期回收失败） | `OnFailure` 私聊管理员 |
| `75` | 只有 `refresh` 会退：上一轮还没结束，本轮跳过 | 同样算正常结束 |

3 和 1 混着记的代价 2026-09-23 在线上看到过：两张单子的到期提醒发不出去，于是一分钟
一轮的 sweep 每分钟退 1、每分钟一条「异常退出，没来得及出报告」的兜底告警 ——
而任务跑得好好的。报警开始说假话，人就学会了忽略它。判「这一行算不算问题」
用 `flows.TROUBLE_WORDS`，**别手写子串**；反过来，新写的失败文案里必须带上其中一个词，
否则这一轮会被当成干净的一轮退 0，告警永远不响。

每个单元都接了 `OnFailure=delivery-unit-failed@%n.service`，进程崩溃或被杀时私聊管理员 ——
任务自己的告警是跑完之后发的，没跑起来就发不出来，一个每天跑两次的任务可以连着挂好几天
没人知道。告警卡片分蓝 / 橙 / 红三级：什么都用红色的话，红色就不再意味着任何事。
