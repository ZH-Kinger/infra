# 云权限面板 · 管理后台改版方案

状态：待 dev 评审 → 拆板执行
适用仓库：`/home/l/桌面/infra`（`src/delivery/`）
写作依据：源码只读通读（前端 `src/delivery/web/*`，后端 `src/delivery/server.py` 及相关模块）
约束：生产系统，**分批上线**，纯原生 JS + 标准库 `http.server`，不引框架、不引构建、不重写整个前端。

用户（唯一管理员）原话是「管理后台的功能太垃圾了吧」，追问后四项痛点全中：
①东西分散找不到 ②不告诉我该干什么 ③不能批量 ④信息不准、看不懂。
本方案按这四条倒推信息架构和任务顺序，第一批不动 IA、只加「待办首页」和改文案，
把痛点②和一半的①在最小风险下消掉。

## ① 现状盘点

### 1.1 管理后台现有页面

导航在 `web/index.html:22-31`，八个 tab；路由在 `web/app.js:163-286`。
默认落点是「申请与开通」（`app.js:133` 的 `space-switch` 指向 `#admin/requests`）。

| # | Tab | 路由 | 代码 | 这一页在回答什么问题 | 有没有操作 |
|---|-----|------|------|---------------------|-----------|
| 1 | 申请与开通 | `#admin/requests` | `web/requests.js:698` | 「谁在申请什么、哪些卡住了」 | 有：重试开通 / 补写登录名到 IAM / 标记失败 / 关单 / 重开 |
| 2 | 人员与名册 | `#admin` `#person=` | `web/app.js:821-1147` | 「公司里谁有哪些云账号、谁权限过大、谁还没对上人」 | 有：确认/驳回对应、分配账号、标服务号、撤销人工记录、收权（预演+执行） |

### 1.2 同一件事被拆到几页（痛点①的根）

**「某人离职了，他的号怎么办」这一件事，现在散在四处，四套口径、四套动作：**

| 位置 | 数据源 | 判据 | 能做什么 |
|------|--------|------|---------|
| 体检 `left` / `unknown` | 权限快照 × 飞书通讯录 | 通讯录里找不到这个人（`hygiene.py:_SECTIONS`） | 什么都不能做，只出清单 |
| IAM 属性表 · 对账 `inactive` | 回读公司 IAM（IT 侧接口） | IT 的 IAM 标了 `is_active=false`（`iam.js:20-25`） | 「确认离职，回收」删登录名+删云号；「稍后处理」3 小时 |
| IAM 属性表 · 待确认删除 | `offboard.json`（定时任务写的） | 强信号已自动停用 / 弱信号只记嫌疑（`offboard.py:1-23`） | 「确认删除」「恢复/没离职」，九章是「我已在控制台处理」 |
| 人员与名册 · 某人详情 | 权限快照 | —— | 「收权」（撤策略/出组），和离职无关但常是同一个人 |

同样，**「这个号是谁的」也散在三处**：人员页的「未关联到人的云账号」（`app.js:1067`）、
人员页的「人工记录」（`app.js:914`）、体检的 `orphan`（认不出属主）。

**「九章的账号」散在三处**：人工登记页（名单）、IAM 属性表页的待确认删除（`BY_HAND`，`iam.js:470`）、
体检（经 `offline_accounts` 参与判断）。

### 1.3 数据源重复或彼此矛盾（痛点④的根）

1. **「无主账号」两套口径、两个数字。**
   `views.py:_unlinked_rows` 列的是「快照里有、名册里没对上的全部子账号」，不做任何过滤；
   体检的 `orphan` 会剔掉服务号和 `tempak-`/`panel-` 这类程序发的号（`hygiene.py:28`）。
   同一个问题，人员页和体检页给出的数字不一样，且没有任何地方解释为什么。

2. **「未停用」在断言一件面板不知道的事。**
   `iam.js:506-508`：`state === "disabled" ? 已停用 : 未停用`。
   这个 `state` 只记录**面板做过什么**（`offboard.py` 的 `disabled`/`suspect`），
   不记录云上现在是什么。管理员在控制台手工停了号，面板照样显示「未停用」——
   这正是用户举的那个例子。

3. **快照里根本没有「能不能登录」这一维。**
   采集器 `inventory_collect.py` 采了 policies / groups / AK（含 `status`、`last_used`），
   **没采登录配置**。所以即便想诚实显示云上状态，今天也拿不到这个字段。
   AK 的 `status` 采到了，但前端没有任何地方用它渲染「这个号的 AK 被停了」。

4. **收权之后页面明说自己是旧的。**
   `app.js:493`：「云上已经变了，这一页的内容要下次采集之后才会更新。」——
   诚实，但对使用者等于「刚做完的事看不见」，只能等第二天。

5. **待办数只有一个，而且藏在二级页。**
   `server.py:1045 admin_todo` 只算 `iam_pending`（离职且登录名还挂着的人数），
   挂在「IAM 属性表」这个 tab 的角标上（`app.js:136-144`）。
   其余七类待办（开通失败、卡住的单、未关联账号、该换的密钥……）在导航上没有任何提示。

6. **陈旧度提示各页各写一套。**
   人员页有 `snapshotLine`（>24h 标红），体检页有 `captured_at` 一行，
   人工登记页有 `stale_days`，IAM 页有「上次对账 X 前」——四套文案、四种阈值，
   而且没有一处把「你现在看到的结论依据的数据有多旧」汇总成一句话。

### 1.4 操作繁琐在哪（痛点③的根）

- 离职处置按 **(平台/账号/登录名)** 一条一条来。一个人有阿里 + 火山 + 九章三个号，
  就是三行、三次 `window.confirm`、三次请求（`iam.js:472-522`）。
- 确认对应 / 驳回 / 分配 / 标服务号，全部逐条 + 弹框（`app.js:31-45`、`app.js:1067-1147`）。
- 唯一已经做对的是云资产页的批量指派（多选 + 底部操作条 + 服务端上限），
  **这套交互就是人员页要抄的模板**，不用发明新的。
- 所有确认都用 `window.confirm`：不能列出「这次会动哪些号」，只能给一句话。
  批量之后这条必然不够用。

## ② 目标信息架构

### 结论

用户倾向的「待办首页 + 人员与账号聚合页」**成立，但只做这两页不够，也不必做成两页**。
建议收敛到 **5 个 tab**（从 8 个降下来），层级只有两层（tab → 详情/抽屉），不加三级页：

| 顺序 | 页面 | 路由 | 主问题 | 主操作 | 由现在的哪些页合并而来 |
|------|------|------|--------|--------|----------------------|
| 1 | **待办** （默认落点） | `#admin` | 现在轮到我处理哪几件事？ | 每项一键处理，或跳到能处理的地方 | 新建；数据来自 offboard / iam 对账 / 申请单 / 名册 / 体检 / health |
| 2 | **人员与账号** | `#admin/people` `#person=` | 这个人在各朵云上是什么状态？这批人怎么一起处理？ | 多选批量（记账类跨人、云侧写按人成组）、收权、确认对应 | 人员与名册 + 体检里与人相关的四类 + IAM 页的离职待确认删除 |
| 3 | **申请与开通** | `#admin/requests` | 谁在申请什么、哪些卡住了 | 重试 / 补写 IAM / 关单 | 原样保留，**不重写** |
| 4 | **资产与密钥** | `#admin/assets` | 云上有什么、分别是谁的、哪些密钥该动 | 批量指派归属、批量提醒本人 | 云资产 + 体检里与物相关的四类（rotate/unused/stray_bucket/stray_dir/abandoned） |
| 5 | **系统与数据源** | `#admin/system` | 平台本身健不健康、上游名单对不对 | 生成 IAM 增量、粘贴九章名单、看配置缺什么 | 系统状态 + IAM 属性表 + 人工登记 + 权限规则 |

### 为什么不是别的分法

- **申请与开通不并进待办页。** 它有自己完整的生命周期（提交→审批→开通→领取→到期），
  是管理员最常主动进入的页，塞进待办只会让待办页变回「堆数据」。
  待办页只摘它的两类异常（开通失败、审批过了没写 IAM）。
- **体检不作为一个页存在，但不删内容。** 体检的八类线索本质是「待办的原材料」，
  它今天是只读孤岛，没人处置（`hygiene.py:3` 自己也写了「处置一律人工做」）。
  改版后：与人相关的四类（`left`/`unknown`/`orphan`/`abandoned`）落到人员页对应的人/无人认领组；
  与物相关的四类落到资产与密钥页。**保留一个「全部线索」视图**（`#admin/system/hygiene` 或
  资产页的折叠区），给「我就想看完整清单」这种需求，不丢东西。
- **IAM 属性表不给它一个一级 tab。** 它是一条对外（IT）的交付流水线，一周走一轮；
  它上面挂着的「离职待确认删除」是和它无关的东西，只是当初没地方放。拆开：
  流水线进「系统与数据源」，离职处置进「人员与账号」和「待办」。
- **层级只有两层。** 任何一件事最多两次点击可达：待办 → 详情/抽屉。
  第三层就是今天「对账藏在 IAM 页里、要点一次按钮才看得见」的复现。

### 过渡策略（生产系统的硬要求）

- 旧 hash 路由**全部保留为别名**：`#admin/hygiene`、`#admin/iam`、`#admin/offline`、`#admin/health`
  继续可达（要么原页、要么重定向到新位置的锚点）。书签和聊天记录里的链接不能 404。
- 新页用**新路由**上线，和旧页并存一段时间；导航先加「待办」，最后一批才删多余 tab。
- 每一批都能单独发布、单独回滚，任何一批被回滚都不影响其余。

## ③ 待办首页

### 3.1 页面结构（从上到下）

1. **一句话结论**：`今天有 3 件要紧的、5 件可以顺手处理的。` 没有就是
   `没有需要你处理的。上一次数据采集 9-23 09:12。`
2. **数据可信度条**（不是待办项，是给下面所有结论打的底）：
   `权限快照 2 小时前 · IAM 对账 6 天前 · 九章名单 12 天前 · 飞书在职状态本次未查`
   任一项超阈值就标黄，并给一个「去刷新」的链接。**哪一项旧，就在依赖它的待办项上标灰降权**。
3. **待办分组**，三组，组内排序见 3.3：
   - 要紧的（安全敞口 / 有人被卡住）
   - 该处理的（台账漂移）
   - 顺手做的（卫生类，默认折叠，只显示汇总行）
4. **已稍后处理**（折叠）：显示「X 件，最早 9-25 回来」。**不是忽略**，到点自己回来。

### 3.2 事项清单

每项的字段固定：`kind / severity / 标题 / 一句话说明 / 主操作 / 次操作 / 依据数据及时间 / 深链`。
说明写「发生了什么 + 不处理会怎样」，不写状态词。

| kind | 来源 | 一句话说明（面板文案） | 主操作 | 次操作 |
|------|------|----------------------|--------|--------|
| `offboard_pending` | `offboard.py:pending()` | 「张三已离职，名下 3 个号已停用，还没删。停用可逆，删号才算收干净。」 | 一起删掉（按人成组，逐条执行） | 他没离职 / 稍后 |
| `offboard_manual` | `offboard.py` `MANUAL_PLATFORMS` | 「李四的九章账号面板动不了，要你去九章控制台停。处理完回来点一下销账。」 | 我已在控制台处理 | 稍后 |
| `iam_inactive` | `iam_sync.cached_reconcile` drift=inactive | 「王五在公司 IAM 里已标离职，云登录名还挂着，他现在还能 SSO 进控制台。」 | 确认离职并回收 | 稍后 3 小时 |
| `request_failed` | `tickets` status=failed | 「2 张申请审批过了但开通失败，申请人在等。」 | 去处理（跳申请页并筛到 failed） | — |
| `request_no_iam` | 单子 `actions.push_iam` | 「赵六的号建好了，但登录名没写进公司 IAM —— 他登不进去。」 | 补写登录名 | — |
| `request_stuck` | `health.py` stuck>30min | 「1 张单超过 30 分钟没进展，可能是定时任务没在跑。」 | 看系统状态 | — |
| `mapping_review` | 名册 `pending` | 「4 个号推断出可能属于某人，还没确认。没确认就不进 IAM 属性表，那个人 SSO 进不去。」 | 去确认（跳人员页，筛待确认） | — |
| `unlinked_account` | `views._unlinked_rows`（与体检 orphan 统一口径后） | 「7 个云账号对不上任何人。出了事找不到人，离职也漏得掉。」 | 去认领（跳人员页无人认领组） | — |
| `iam_increment` | `iam_sync.preview` | 「有 5 行属性变化没发给 IT，其中 2 行是删号。不发的话离职的人属性一直留在公司 IAM。」 | 生成增量 | — |
| `iam_stale_pending` | `iam_sync` pending 存档 > 7 天 | 「有一份增量发出去 9 天了，IT 还没回确认。确认之前基线不动，之后每次算的差异都是虚的。」 | 去催 / 作废 | — |
| `keys_rotate` / `keys_unused` | 体检 rotate/unused | 汇总一行：「12 把密钥该换、5 把没人用。提醒本人处理，别代劳。」 | 批量提醒（跳资产与密钥页） | 稍后 30 天 |
| `data_stale` | 快照/对账/九章名单超期 | 「权限快照 3 天没更新了，下面这些结论都可能是旧的。」 | 看系统状态 | — |
| `config_blocking` | `health.py` crit | 「缺 XXX 配置，凭证发放整条链路发不出去。」 | 看系统状态 | — |

体检的 `stray_bucket` / `stray_dir` / `abandoned` **不进待办**：它们不是「轮到你处理」的事，
是「需要找人问清楚」的调查线索，放资产与密钥页。硬塞进待办只会让待办页重新变成清单页。

### 3.3 排序规则

**三个键，依次比较：**

1. **后果等级**（决定分组，不是可调的）
   1. 安全敞口：离职的人还能登、无主的高危权限 →「要紧的」
   2. 有人被卡住：开通失败、登不进去、等确认才能用 →「要紧的」
   3. 台账漂移：对应不上、没登记、增量没发 →「该处理的」
   4. 卫生：密钥老化 →「顺手做的」
2. **挂了多久**（同级内降序）：用事项自己的时间戳（`offboard.at` / 单子 `created_at` /
   对账 `checked_at`），越久越靠前。
3. **一次能清多少**（同级同龄）：可批量处理的排前面 —— 让管理员点一次清掉一批，
   而不是先被一条一条的事消耗掉耐心。

**两条覆盖规则：**

- **依据数据过旧的项降权并标注**：比如飞书在职状态本次没查，那么所有基于「通讯录里找不到」
  的项一律标灰、不进「要紧的」，文案写明「本次没查在职状态，这条不作数，只是提醒」。
  拿不到状态却照排第一位，就是今天体检页「查不了就不判断离职」那条规矩的反面。
- **数量收敛**：同 kind 超过 5 条折成一行汇总（「另有 8 条同类」），点开展开。
  待办页一屏能看完才叫待办页。

### 3.4 一键操作的边界

待办页上只放**两类**按钮：

- **记账类**（不动云）：稍后处理、他没离职、我已在控制台处理、标为服务号。就地完成、就地消失。
- **跳转类**：跳到能处理它的地方，并**带上筛选条件**（例：`#admin/people?todo=offboard`）。

**动云的写操作（删号、停号、收权）不在待办页直接执行**，一律跳到人员与账号页的预演界面。
理由：待办页是「扫一眼」的场景，人在扫的时候点错的概率最高，而删号不可逆。
唯一例外是「按人成组」的确认删除，它跳到人员页后自动打开那个人的确认面板并预勾选——
点击路径没变长，但确认的时候看得见「会动哪三个号」。

## ④ 人员与账号页

### 4.1 主表

一行 = 一个人（名册里的人）；表尾附加一个「无人认领的账号」分组（今天的 `unlinked`）。

| 列 | 内容 | 说明 |
|----|------|------|
| 姓名 / 邮箱 | 同今天 | |
| 在职 | `在职` / `已离职（IT IAM 9-20）` / `通讯录查不到` / `未查` | 三态，来源和时间写在 title 上 |
| 账号 | 每个平台一个 chip：`阿里 zhangsan` `火山 zhangsan` `九章 wuji-zhangsan` | chip 上带状态点，见 4.4 |
| 密钥 | `3 把 · 1 把该换` 或 `没采到` | 来自快照 `keys`，`None` 显示「没采到」 |
| 高危 | 同今天 | |
| union_id | 同今天 | |
| 待办 | 这个人身上挂着几件待办，点击展开 | 和待办页同一份计算 |

### 4.2 批量：能批什么、不能批什么

**批量的单位有两个**：跨人（选多行）和按人成组（选一行，作用于他名下全部账号）。

| 操作 | 跨人批量 | 按人成组 | 上限 | 为什么 |
|------|---------|---------|------|--------|
| 稍后处理 / 他没离职 / 标为服务号 / 驳回对应 / 撤销人工记录 | 允许 | 允许 | 200 | 纯记账、可撤销、不动云 |
| 确认对应（分配给某人） | 允许（分配给同一个人时） | —— | 50 | 写名册，可撤销 |
| 提醒本人（换密钥/密钥没人用） | 允许 | 允许 | 50 | 只发飞书；`nudge.py` 自带 14 天节流 |
| 确认离职并回收登录名（改 IAM 属性表待发内容） | 允许 | 允许 | 10 人 | 改的是待发增量，发出去之前还能改；但它会连带触发删云号，所以压到 10 |
| **停用**（关登录、禁 AK，可逆） | 允许 | 允许 | 10 人 / 30 账号 | 可逆，且这是离职响应里最该快的一步 |
| **恢复**（把停用时关掉的开回去） | 允许 | 允许 | 10 人 | 可逆 |
| **删号**（`delete_user`，不可逆） | **不允许** | **允许**（一个人名下多个号一起删） | 1 人 / 一次最多 5 个号 | 见下 |
| **收权**（撤策略/出组） | **不允许** | **不允许** | —— | 每次要看「撤完还剩什么」，这是一次判断，不是一次操作 |

**删号只允许「按人成组」，不允许跨人批量**，这是本方案里最重要的一条边界：

- 用户抱怨的真实场景是「一个人名下阿里/火山/九章三个号要点三次」——按人成组正好解决它。
- 跨人批量删号解决不了任何真实痛点（一次删 10 个人的号不是日常），却把一次误操作的代价
  从「一个人停摆」放大到「十个人停摆」，而删号不可逆。
- `offboard.py:51` 的 `MAX_AUTO_PEOPLE = 3` 已经为无人值守场景设了这条线，
  人工场景放宽到「一个人的全部号」是合理的，放宽到跨人不是。

### 4.3 批量的安全护栏

1. **预演先行（所有动云的批量）。**
   先 POST 一次 `preview`，服务端返回三段：**会动的**（逐条列出平台/账号/登录名）、
   **不会动的及原因**（受保护 `offboard.protected()`、归属存疑 `unverified`、已经是终态、
   平台没接口）、**做完之后是什么样**。选择一变，预演作废（照 `app.js:474` 的 revokeBox 做法）。
2. **二次确认对话框必须列出条目**，不能用 `window.confirm`。文案模板：

   > **确认删除张三名下的 3 个云账号？**
   > · 阿里云 1704… `zhangsan`
   > · 火山引擎 2100… `zhangsan`
   > · 九章 `wuji-zhangsan`（面板动不了，只记账）
   > 会删掉账号本身（先出组、摘策略、删 AK）。他在桶里的文件、数据集、实例都不动。
   > **删了不能恢复。**
   > 请输入「张三」确认：[____]

   - 可逆操作（停用/恢复/记账）：不要求输入确认词，但必须列出条目。
   - 不可逆操作（删号）：要求输入**这个人的姓名**（不是 `DELETE`，姓名能同时防「选错人」）。
   - 超过 10 条时折叠显示前 10 条 + 「另有 N 条」，但总数必须在标题里。
3. **服务端独立校验上限和白名单**，不信前端：
   - 每个 op 的条数上限在服务端常量里（照 `server.py:100 _OWNER_BATCH_MAX` 的写法，
     前端常量注释写明「和服务端对齐」）。
   - 删号只认 `offboard.json` 里存在的记录键（`offboard.decide()` 今天已经这么做，保持）。
   - `protected()` / `unverified` 在服务端再拦一次。
4. **逐条执行、逐条结果、失败不阻断其余**。返回 `{done:[], failed:[{key, error}], skipped:[{key, why}]}`，
   结果面板直接给「重试失败的 N 条」。云操作没有回滚，不要假装有事务。
5. **留痕**：一次批量写一条 `review.log`（`review.log_offboard` 已有），内含全部条目和 actor。
6. **幂等**：请求带 `client_op_id`；服务端对已处于终态的条目返回 `skipped: 已处理过`，不报错。
   页面上重复点、断网重发都不会删第二次。
7. **勾选跟随筛选**：重画后把已不在结果集里的选中项剔掉（`assets.js:504-506` 已有正确做法，
   注意别复现 notes 里记的「超 500 行的勾选看不见却会被指派」那条缺陷）。
8. **按钮在预演出来之前一律 disabled**，执行中禁用并显示进度（`3/8 已完成`）。

## ⑤ 信息准确性

### 5.1 三态是底线

面板已经在数据层把三态做对了（`keys=None` 表示没采到、`last_used_known`、`status_checked`），
但**展示层把三态压成了两态**。规则：任何状态标签只能是
**已知真 / 已知假 / 不知道**，「不知道」不许渲染成「否」。

### 5.2 什么时候读快照、什么时候查云

| 场景 | 数据来源 | 理由 |
|------|---------|------|
| 页面加载、列表渲染、待办计算 | 快照 + 本地文件，**零云调用** | `inventory.py:1-12` 的取舍成立：页面必须秒开，且一个页面级的云调用会被每次刷新放大 |
| 某一条记录的「现在查一下云上」按钮 | 实时读云（单个用户） | 人主动点，一次一个对象，成本可控 |
| 任何批量写操作的预演 | 实时读云 | 预演要说的是「现在会发生什么」，拿旧快照预演等于骗人 |
| 写操作完成后 | 实时回读该对象并就地更新 | 替掉今天那句「要下次采集之后才会更新」（`app.js:493`） |
| 离职待办的自愈核对 | 定时任务里实时读云 | 每轮对 pending 记录核一次，见 5.3 |

**不做**：页面自动轮询、列表级实时查云、后台定时全量实时查。

> 需要 dev 留意的事实：`inventory.py` 开头写「看板根本不持有云凭证」，但 `provision.executor_from_env`
> 就在面板进程里，`offboard` 的停号/删号是面板直接调云的。**这句话今天已经不成立**。
> 上面的取舍是按「能查但要省着查」定的，不是按「查不了」定的。这条要同步更新到模块说明里，
> 否则下一个人会照着一句过期的注释做设计。

### 5.3 面板外发生的变更怎么体现

三条路，从便宜到贵：

1. **采集补一维（治本）**：采集器加 `login_enabled`（阿里/火山的 `GetLoginProfile`），
   AK 的 `status` 已经有了但前端没用。快照里有了这两个，「这个号还能不能登、密钥还活着没」
   第二天就自己对上了。旧快照缺字段 = 未知，不是 false。
2. **待办自愈（治标但立竿见影）**：定时任务每轮对 `offboard.json` 里 pending 的记录
   做一次轻量核对（`GetUser` / `GetLoginProfile`）：
   - 云上已经没这个号 → 记 `DELETED`，`decided_by = "云上已不存在"`，从待办消失
     （`offboard.auto_disable` 对 `gone` 已经这么做，把同一套逻辑搬到 pending 核对上）。
   - 云上已经是停用态 → 记 `external_disabled = true`，标签改成「已停用（控制台）」。
   - 核对失败 → **只记 `checked_error`，绝不改状态**。查不到不等于没有。
3. **就地回读**：面板自己做完写操作，立刻回读一次并更新记录与页面。

### 5.4 状态标签文案表（给 dev 照抄）

| 今天写的 | 改成 | 为什么 |
|---------|------|--------|
| `未停用` | `面板没停过它` + 第二行 `云上：仍可登录 / 已停用 / 未知（采于 9-23 09:12）` | 原文在断言云上状态，而面板不知道 |
| `已停用` | `已停用（面板 9-20）` 或 `已停用（控制台）` | 谁停的要能看出来，否则「恢复」按钮该不该点没人知道 |
| `快照中不存在` | 保留，补一句 `可能已在控制台删除，也可能这个云账号本次没采到` | 今天的 `acct.gone` 文案已经这么写了，保持 |
| `已完成` / `已删除` | `已删除云账号（桶里的文件、数据集、实例都没动）` | 删号最容易被误解成删数据 |
| 高危 `3` | 保留数字，title 里写清是「直接授予 + 经组继承」 | |
| `12 人` 这类统计 | 一律带口径：`12 人（只算名册里已确认归属的号）` | |
| 没采到的任何一栏 | `没采到 —— 不能据此认为没有` | 今天 `keys` 已有这条规矩，推广到全部 |
| `要去控制台停` | `面板动不了九章，要你去九章控制台停；处理完回来点一下销账` | 状态词换成动作 |

统一规则：**标签 = 事实 + 谁说的 + 什么时候**。凡是只有事实、没有来源和时间的标签，一律重写。

## ⑦ 明确不做

1. **不引前端框架、构建工具、组件库。** 沿用 `core.js` 的 `h()/api()/apiPost()`，
   沿用「接口字段只经 textContent / 属性赋值进 DOM」这条安全约定，一字不改。
2. **不重写申请与开通页。** 它今天工作正常，只从它取两类异常进待办。
3. **不做自动删号，不放宽任何自动处置闸门。** `offboard.MAX_AUTO_PEOPLE = 3` 保持；
   自动的只有「停用」（可逆），删号永远要人点头。
4. **不做跨人批量删号、不做跨人批量收权。** 理由见 4.2。
5. **不做页面级实时查云、不做自动轮询刷新。** 只有三种情况打云：单条「现在查一下」、
   批量预演、写操作后回读。
6. **不做多管理员、角色、审批流、工单指派。** 现在只有一个管理员，加这些是空转。
7. **不做趋势图、报表、统计大盘。** 今天人员页顶部那排 `stats` 保留但下沉，
   待办页不放任何统计数字（统计不是待办）。
8. **不改快照的存储形态**（不引数据库），不改采集与展示分离的架构。
9. **不为面板新写第二份判据。** 体检、离职、对账的判断逻辑继续和 CLI 共用同一个模块；
   页面只负责显示和调用。出现「网页说 A、命令行说 B」比功能缺失更糟。
10. **不做移动端专门布局**，沿用现有响应式。
11. **不动飞书审批链路、凭证发放链路**。本次只改管理后台的信息架构与交互。

## 给 dev 的落地提示（只读源码得到的、会踩的点）

- 人员页的批量交互直接抄 `web/assets.js:429-525`，但**注意 notes.md 已记的两条缺陷**：
  `chips()` 是死代码；超过 500 行截断后「看不见的勾选仍会被提交」。新页别复制这两条。
- `app.js` 零 export 且 import 即 `boot()`，前端无法直接单测（notes 已记）。
  新页面（待办 / 人员与账号）**请单独成模块并 export 渲染函数**，照 `requests.js` / `assets.js`
  末尾那种「导出只为可测」的做法，否则这一批又是零覆盖。
- 待办的排序与分组放服务端（AC-1），前端只渲染。放前端的话 CLI 和飞书推送就得各写一份。
- `iam.js` 的 `offboardSection` 迁走时注意 `BY_HAND`（九章）分支的两套确认文案，
  它是唯一说清「面板没动云」的地方，别在迁移中丢掉。
- `_require(admin=True)` + `_same_origin_json()` 这两道门在新接口上一个都不能少。
- 批量接口的上限常量放服务端，前端常量加注释「和服务端 XXX 对齐」（照 `_OWNER_BATCH_MAX` 的先例）。
