状态：**已定稿**（2026-09-22）。现状实测数据见附录 `oss-storage-survey-20260921.md`。

## 二、目录结构

```
供应商交付桶  oss://wuji-provider-hz/
├── third-party-data/<供应商>/<批次ID>/      供应商交付的 raw 数据，待 QC
├── internet/<来源>/<批次ID>/                供应商交付的互联网数据，待 QC
└── qc/<数据类型>/<来源>/<批次ID>/           QC 没过的，不删（索赔证据）

原始数据桶    oss://wuji-bucket-hangzhou/   ·   oss://wuji-sing/
├── third-party-data/<供应商>/<批次ID>/      QC 通过后由数据管线落盘
├── internet/<来源>/<批次ID>/
├── public-datasets/<数据集名>/              开源数据集
├── teleop/<设备或场地>/<批次ID>/            训练调用的真机数据备份
└── general/                                 通用 / 共享、待认领

处理后的数据桶  oss://wuji-processed-hz/   ·   oss://wuji-processed-sing/
├── label/<来源>/<版本>/<批次ID>/            标注成品（LeRobot parquet）
├── processed/<来源或项目>/<批次ID>/         加工、格式转换、重定向产出
└── tmp/<来源或项目>/<批次ID>/               临时，7 天自动清

回传桶  oss://wuji-data-tran/
├── volcano/                                 第一层：从哪朵云 / 哪个地域回来
│   ├── third-party-data/<供应商>/<批次ID>/  第二层起：和原始桶一字不差
│   ├── internet/<来源>/<批次ID>/
│   └── teleop/<设备或场地>/<批次ID>/
├── aliyun-sing/
│   └── third-party-data/<供应商>/<批次ID>/
├── qc/<云>/<数据类型>/<来源>/<批次ID>/      核对没过的，结构与上面一一对应，不删
├── staging/<任务ID>/                        搬运中转（PFS 直传等），7 天清
└── general/<登录名>/                        存量人名目录，只认领不新增

数据工厂  oss://data-factorys/<批次ID>/

个人开发空间  oss://wuji-algo-dev-<地域>/
├── <组>/<人>/
│   ├── ckpt/<实验名>/
│   └── 〔其余自己安排〕
└── general/                                 通用 / 共享
```

每个批次根目录放一个 `_manifest.json`：谁传的、是什么、批次说明、QC 结论。

## 三、五条规则

**① 数据类型只有一张词表，所有桶共用。**
`third-party-data`、`internet`、`public-datasets`、`teleop`、`label`、`processed`……
都从同一张表里取。**新增数据类型要走审批**（面板的「新增数据类型」申请）。
加一个词就够了：各桶的目录结构、权限、清理规则都是按层级写的，自动覆盖新类型。

**② 每种类型的层级登记在词表里，同一种类型在所有桶里一模一样。**
默认是 `<来源>/<批次ID>/`；少数类型不同，也在词表里写明：

| 类型 | 层级 |
|---|---|
| `third-party-data` | `<供应商>/<批次ID>/` |
| `internet` | `<来源>/<批次ID>/` |
| `teleop` | `<设备或场地>/<批次ID>/`（原先少了这一层，已补上） |
| `public-datasets` | `<数据集名>/` |
| `label` | `<来源>/<版本>/<批次ID>/` |
| `processed` | `<来源或项目>/<批次ID>/` |

层级登记了，写权限才能按层签（比如统一签到 `<类型>/<来源>/`），核对工具才知道去哪层找
`_manifest.json`，面板建目录时才知道要问几个问题。**同一个类型在两个桶里层级不同，
「只换桶名」就不成立了** —— 这是它必须登记、不能各桶自己定的原因。

**③ 搬运只换桶名，路径一个字不改。**
- 供应商交付桶 → 原始桶：`third-party-data/<供应商>/<批次ID>/` 原样落进原始桶。
- 回传桶 → 原始桶：去掉第一层 `<云>/`，剩下的和原始桶一字不差。
- 杭州 ↔ 新加坡：结构相同，路径相同。

路径在搬运中被改写 = bug。它会让血缘断掉（血缘靠批次 ID 贯穿），
也让「源的每个文件在目的都在」这条核对没法做。

**④ 一个目录名只有一个意思。**

| 名字 | 意思 | 清理 |
|---|---|---|
| `general/` | 通用 / 共享、待认领 | 不自动清，体检报超 90 天或超 10 GiB 的 |
| `tmp/` | 临时 | 7 天自动清 |
| `staging/` | 搬运中转 | 7 天自动清 |
| `qc/` | QC / 核对没过的数据 | **不清**，那是索赔和追责的证据 |

同一个名字表示两件事，按前缀写的权限和清理规则迟早会把「共享数据」当临时目录清掉。

**⑤ 人只写两处：自己的开发空间、`general/`。**
其余前缀只有流程身份能写。回传方、供应商只能写自己那一格，看不到别人的，更看不到主本。

## 四、各桶配置（2026-09-22 新建的三个已按此配好）

所有数据桶：私有、阻止公共访问、开版本控制、服务端加密（SSE-OSS，AES256）、
没传完的分片 7 天清。

| 桶 | 冗余 | 旧版本保留 | 其他规则 |
|---|---|---|---|
| `wuji-provider-hz` | ZRS（交付数据丢了拿不回来） | 90 天 | — |
| `wuji-processed-hz` | LRS（和杭州主桶一致，能升 ZRS，反过来不行） | 30 天 | `tmp/` 7 天 |
| `wuji-processed-sing` | ZRS（和 wuji-sing 一致） | 30 天 | `tmp/` 7 天 |

`wuji-bucket-hangzhou`（859.7 TiB）开着版本控制、没有旧版本清理规则：
**已决定维持现状，不配**（2026-09-22）。

## 五、存量

**不搬，只登记、认领。**

- 各桶里现有的人名一级目录：原地不动，等本人认领后自己搬到开发空间。
- `wuji-data-tran` 桶根下的 `lightwheel/`（1070 个任务目录，供应商交付）、
  `vitra_sft_…`（整套 ckpt）等：原地登记，认领归位。
- `wuji-sing`、`wuji-bangkok` 里有杭州没有的前缀（实测曼谷 5/5 都是孤本）：
  **它们是孤本不是副本**，任何清理规则上线前都要先确认。

## 六、要跟着改的配置

- 机器人的 `PFS_STAGING_MAP`：CPFS 那侧的中转从 `oss://wuji-data-tran/` 桶根改到 `staging/`。
- 开发空间的 `general/` 组：维持「通用 / 共享」这个意思，不再兼作临时目录。
- 面板：数据类型词表、「新增数据类型」审批入口、「新建数据目录」改用新词表。

## 七、还没定的

- 数据回传核对通过后，自动搬还是人工确认后再搬（倾向自动搬，单批超 1 TB 等人确认）。
- 泰国那条链以后的产出要不要经 `wuji-data-tran` 回来。
- 对外交付 / 发布物（不可变、长期保留）放哪。
